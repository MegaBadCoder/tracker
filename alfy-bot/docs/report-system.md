# Система отчётов — архитектура и логика

## Концепция: «призраки» (Ghost Model)

Система работает без таблицы `reports`. Отчёт — это **не запись в БД**, а вычисляемое состояние:

- **Расписание** (`goal_schedules`) определяет, какие вопросы должны быть заполнены в какие дни
- **Ответы** (`report_answers`) хранят факты заполнения с полем `scheduled_date`
- **Нет записи = не заполнено** — пропущенные даты вычисляются на лету

```
┌─────────────────┐     ┌──────────────────┐     ┌──────────────────┐
│  GoalQuestion    │────▶│  GoalSchedule    │     │  ReportAnswer    │
│                  │     │                  │     │                  │
│  question: text  │     │  frequency_type  │     │  user_id         │
│  type: rating    │     │  days_of_week    │     │  question_id     │
│  can_skip: false │     │  interval_days   │     │  scheduled_date  │
│  order_index: 0  │     └──────────────────┘     │  answer_text     │
│  is_active: true │                              │  answer_number   │
└─────────────────┘                              │  answer_bool     │
                                                  └──────────────────┘
```

## Расписание (ScheduleService)

Каждый вопрос может иметь расписание. Метод `isQuestionDueOnDate(question, goalStart, date)` определяет, нужно ли задавать вопрос в конкретный день:

| frequency_type | Логика | Пример |
|---|---|---|
| `daily` | Каждый день | — |
| `weekly_days` | По дням недели | `[1, 3, 5]` = Пн, Ср, Пт |
| `interval` | Каждые N дней от старта цели | `interval_days: 3` = каждый 3-й день |
| Нет расписания | Считается `daily` | — |

---

## Типы вопросов

| Тип | Ввод | Кнопки | Нормализация |
|---|---|---|---|
| `text` | Свободный текст | — | `answer_text` |
| `number` | Число текстом | — | `answer_number` (парсится) |
| `rating` | Кнопки 1–5 | `[1] [2] [3] [4] [5]` | `answer_number` |
| `emoji_rating` | Кнопки-эмодзи | `[😕] [😐] [🙂] [😊] [🔥]` | `answer_text` |
| `yes_no` | Кнопки Да/Нет | `[Да] [Нет]` | `answer_bool` |
| `time_spent` | Кнопки диапазонов | `[<30м] [30-60] [1-2ч] [2+ч]` | `answer_text` |

Кнопки генерируют callback `answer_{значение}`. Для `text` и `number` бот ждёт текстовое сообщение.

## Сессия заполнения (ReportScene)

### Шаг 1: Вход в сцену

```
Пользователь → /report или кнопка «Создать отчёт»
         ↓
Загрузить все активные цели пользователя
         ↓
Для каждой цели:
  - Есть ли вопросы, запланированные на сегодня? (ScheduleService)
  - Все ли обязательные вопросы уже отвечены? (ReportService.isDateFilled)
         ↓
Показать список незаполненных целей
```

### Шаг 2: Выбор цели

```
Пользователь выбирает цель
         ↓
Проверить: есть ли пропущенная дата? (findLastUnfilledDate)
         ↓
┌─ Есть пропуск ──────────────────────────────────────┐
│  «За 20 февраля есть незаполненный отчёт»           │
│  [Заполнить]  [Пропустить]  [Отменить]              │
│                                                      │
│  Заполнить → startReport(goal, '2026-02-20')        │
│  Пропустить → startReport(goal, сегодня)            │
│  Отменить → выход из сцены                          │
└──────────────────────────────────────────────────────┘
         ↓
┌─ Нет пропуска ──────────────────────────────────────┐
│  startReport(goal, сегодня)                         │
└──────────────────────────────────────────────────────┘
```

### Шаг 3: Заполнение вопросов

```
Загрузить неотвеченные вопросы на targetDate
(getUnansweredQuestions: расписание → due-вопросы → минус уже отвеченные)
         ↓
Цикл по вопросам:

  📊 Вопрос 1 из 3

  На сколько ты работал сегодня по этой цели?
  [1] [2] [3] [4] [5]
  [⏭ Пропустить]         ← только если can_skip = true

         ↓ (ответ кнопкой или текстом)

  reportService.addAnswer(userId, questionId, targetDate, ответ)
         ↓
  Удалить сообщение с вопросом → показать следующий
```

### Шаг 4: Завершение

```
Все вопросы отвечены
         ↓
«✅ Отчет сохранен!»
         ↓
┌─ Был пропуск, который пользователь пропустил? ─────┐
│  Да → startReport(та же цель, сегодня)              │
│  Нет → offerNextGoal()                              │
└──────────────────────────────────────────────────────┘
         ↓
offerNextGoal():
  Найти другие активные цели с незаполненным отчётом
         ↓
┌─ Есть ещё цели ─────────────────────────────────────┐
│  «Есть ещё цели для отчёта:»                       │
│  «1. Фитнес»                                        │
│  «2. Учёба»                                         │
│  [1] [2] [❌ Нет, спасибо]                          │
└──────────────────────────────────────────────────────┘
         ↓
┌─ Все цели закрыты ──────────────────────────────────┐
│  «🎉 Все цели закрыты!» → выход из сцены           │
└──────────────────────────────────────────────────────┘
```

## Определение заполненности (ReportService)

### isDateFilled(goalId, date)

Дата считается заполненной, когда **все обязательные** (`can_skip = false`) вопросы, запланированные на эту дату, имеют ответы в `report_answers`.

```
Вопросы цели
  → фильтр: is_active = true И can_skip = false
  → фильтр: isQuestionDueOnDate(вопрос, дата)
  → считаем сколько из них имеют ответы
  → заполнено = (отвеченных >= обязательных)
```

Необязательные вопросы (`can_skip = true`) **не блокируют** заполненность.

### getUnansweredQuestions(goalId, date)

Возвращает **все** активные due-вопросы (и обязательные, и необязательные), на которые ещё нет ответов. Используется для построения списка вопросов при заполнении.

### findLastUnfilledDate(goalId)

Ищет последнюю пропущенную дату. Алгоритм:

```
Начинаем со вчера, идём назад к goal_start:
  ↓
Нашли дату с due-вопросами?
  ├─ Да, не заполнена → вернуть эту дату (пропуск!)
  ├─ Да, заполнена → вернуть null (всё ок, последняя заполнена)
  └─ Нет → идти дальше назад
```

Правило: можно заполнить **только последний** пропущенный день. Более старые пропуски остаются незаполненными навсегда.

## Сохранение ответа (addAnswer)

```typescript
addAnswer(userId, questionId, scheduledDate, answerText)
```

1. Загрузить вопрос → определить тип
2. Нормализовать ответ:
   - `number` / `rating` → парсить в `answer_number` (поддержка запятой: `4,5` → `4.5`)
   - `yes_no` → парсить в `answer_bool` (`да/yes/true/1` → `true`)
   - Остальные → только `answer_text`
3. Сохранить в `report_answers` с `scheduled_date` (дата, на которую заполняем, не текущая)

## Аналитика (getQuestionAnalytics)

Строит timeline для графика на фронтенде:

```
1. Загрузить вопрос и цель, проверить доступ
2. Определить диапазон: goal_start → min(goal_end, сегодня)
3. Одним SQL-запросом достать все ответы за диапазон
4. Построить Map<дата, ответ> для O(1) поиска
5. Итерировать день за днём:
   ├─ Дата в расписании + есть ответ → { filled: true, данные }
   ├─ Дата в расписании + нет ответа → { filled: false, placeholder }
   └─ Дата НЕ в расписании → пропустить (не включать в результат)
```

Placeholder для пропущенных дат:
- Числовые типы (`number`, `rating`) → `answer_number: 0` (чтобы график не рвался)
- Текстовые → `answer_text: "Не было заполнено"`

## Структура данных сессии

```typescript
{
  goalId: 12,                    // Текущая цель
  userId: 1,                    // ID пользователя в БД
  targetDate: '2026-02-22',     // На какую дату заполняем (может быть вчера)
  currentQuestionIndex: 0,       // Текущий вопрос (0-based)
  questions: [GoalQuestion[]],   // Неотвеченные due-вопросы
  lastQuestionMessageId: 150,    // Для удаления сообщения после ответа
  preselectedGoalId: 12,         // Если вошли через кнопку конкретной цели
  pendingCurrentGoalId: 12,      // Цель для сегодня (после заполнения пропуска)
}
```
