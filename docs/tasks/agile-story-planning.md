# Планирование историй в Agile-бэклоге

**Status:** done
**Branch:** feat/agile-board
**Worktree:** .worktrees/feat-agile-board
**Goal:** В локальном Agile-проекте пользователь фильтрует бэклог по эпику, видит раскрываемые истории внутри спринтов, назначает релиз пустой истории и создаёт в ней задачу с наследуемым релизом.
**Mode:** interactive

## Context
- `ProjectBacklogView` выводит плоские списки задач по спринтам; `BacklogEpicsPanel` открывает карточки групп, но не фильтрует список.
- `BoardGroup` не хранит релиз; `GroupActionsMenu` вызывает назначение релиза существующим задачам группы.
- Спринт и релиз задачи независимы; выпущенные релизы и закрытые спринты защищены от новых назначений.

## Design
Первый этап: раскрываемые истории в спринтах и бэклоге, фильтр по эпику, собственный плановый релиз истории. Релиз доступен в строке и карточке истории; создание задачи внутри истории наследует его на сервере, если вызывающий не передал `releaseId` (явный `null` означает без релиза). Эпик остаётся контейнером, способным охватывать несколько релизов.

Спринт истории пока определяется её задачами: история показана в каждом блоке, где есть её задачи, с прогрессом по задачам этого блока. Пустые истории показаны в бэклоге. Задачи непосредственно в эпике или без группы остаются отдельными строками. Добавление задачи из строки истории передаёт её группу и спринт блока.

Фильтр панели: «Все», конкретный эпик, «Без эпика»; выбор подсвечен, применяется ко всем блокам, открытие карточки — отдельное действие. Счётчик заголовка спринта сохраняет общий объём, при фильтрации отдельно показано количество видимых задач. Управление спринтом использует полный набор задач.

Назначение релиза истории сохраняет связь и назначает текущие задачи, кроме задач выпущенных релизов. Старое массовое действие эпика сохраняется и назначает плановый релиз его историям. Снятие релиза очищает план истории и назначения её задач вне выпущенных релизов. Новые задачи в истории с уже выпущенным релизом требуют выбора нового релиза либо явного `null`.

При выпуске релиза незавершённые истории следуют выбранному переносу; завершённые сохраняют связь. При удалении релиза связь очищается, истории и задачи сохраняются. Все связанные изменения выполняются атомарно.

Совместимость: nullable `BoardGroup.releaseId`, старым историям присваивается `null`, релиз по существующим задачам автоматически не угадывается. Существующие явные назначения задач сохраняются. Фильтр по релизу, собственный спринт истории и перетаскивание истории целиком отложены.

Альтернативы: только группировка и фильтр дешевле, но не позволяют запланировать пустую историю; превращение истории в тип задачи объединяет модель планирования, но требует более широкой миграции API и данных. Выбранное расширение текущей модели обратимо и решает согласованный первый этап.

TDD: yes — серверные назначения, наследование, жизненный цикл релиза и вычисление группировки имеют проверяемые контракты; визуальная пригодность подтверждается отдельно в браузере.

### Invariants
- IV1 — История и её релиз принадлежат одному проекту; новое назначение выпущенного релиза запрещено.
- IV2 — Массовое назначение и очистка не переписывают задачи выпущенных релизов; выполненные задачи при выпуске остаются на месте.
- IV3 — Явное значение `releaseId`, включая `null`, имеет приоритет над наследованием.
- IV4 — Фильтрация не меняет данные, итоговые счётчики и последствия завершения спринта.
- IV5 — Каждая задача блока отображается ровно один раз; пустая история доступна в бэклоге.
- IV6 — Выпуск и удаление релиза не удаляют истории и задачи; записи связанных изменений атомарны.

### Principles
- PC1 — Плановый релиз истории хранится на сервере (GPC4); UI использует существующие stores и picker-компоненты (GPC8).
- PC2 — Группировка не вводит отдельный источник спринта истории; разделённая между спринтами работа остаётся видимой.

### Unknowns
- UK1 — Решено: `TypeOrmReleaseRepository` уже использует `DataSource.transaction`; назначение и снятие релиза группы будут использовать ту же границу транзакции.

## Conclusion
### Outcome
- Цель подтверждена через UI: пустая история назначена в релиз, видна в его составе, новая задача унаследовала релиз после перезагрузки. Фильтры эпика, разбиение истории между спринтами и перенос задач проверены в отдельном проекте.
- Независимое ревью обнаружило два важных сценария: создание задачи в выпущенной истории и drop в чужую историю. Оба воспроизведены регрессионными тестами и исправлены; повторное ревью не нашло важных замечаний. Создание в выпущенной истории теперь отправляет явный `releaseId: null` с подсказкой в UI, подтверждено браузером и сохранёнными данными. Drop принимает только задачи той же истории; перенос между спринтами сохраняет `groupId`.
- Финальные проверки: 665 серверных unit-тестов, 80 HTTP e2e и 844 теста фронта; обе проверки типов и lint затронутого фронта прошли. Временный проект и его задачи удалены; рабочий бэклог открыт, dev-серверы оставлены запущенными.
- Небольшое ограничение: если нажать создание до загрузки списка релизов, сервер может отклонить запрос для выпущенной истории; ошибка отображается, после загрузки создание работает. Мобильная визуальная проверка не подтверждена.
- Реализация сохранена в ветке `feat/agile-board`. Слияние и публикация PR отложены до просмотра пользователем.
