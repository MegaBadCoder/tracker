# Порядок и приоритет эпиков и историй

**Status:** done
**Branch:** codex/epic-story-order
**Worktree:** /Users/v/projects/Alfy/.worktrees/epic-story-order
**Goal:** Пользователь прямо на доске стрелками вверх/вниз меняет порядок эпиков проекта и историй внутри выбранного эпика; порядок сохраняется после перезагрузки и одинаково читается в клиенте и MCP. Useless if: управление доступно только вне доски; сортировка действует только локально; истории смешиваются между эпиками; MCP и клиент показывают разный порядок.
**Mode:** interactive

## Context
- Следующая фаза после MCP CRUD эпиков и историй (PR #45); пользователь запросил workflow up:make.
- BoardGroup уже хранит order; REST имеет PATCH /projects/:projectId/groups/reorder, клиент — group-store.reorderGroups.
- MCP пока не публикует изменение порядка групп; отдельного поля priority у групп нет.
- Текущая реализация reorder проверяет доступ к проекту, но обновляет переданные UUID без ограничения проектом и без проверки общего родителя; записи не объединены транзакцией.

## Design
Место управления — непосредственно доска проекта: стрелки в заголовках эпиков и историй внутри эпика. Перестановка меняет вертикальный порядок групп на доске, а не порядок колонок или задач.

Пользователь уточнил: ручное перемещение стрелками вверх/вниз, например 1, 2, 3, 4 → 3, 4, 1, 2. Позиция в списке задаёт очередность; отдельное поле priority и вычисление приоритета из историй не нужны. Стрелки у эпиков меняют порядок эпиков проекта, стрелки у историй — порядок внутри родительского эпика. У первого элемента недоступно перемещение вверх, у последнего — вниз. Порядок сохраняется на сервере; ошибка сохранения восстанавливает прежний порядок и показывается пользователю. Переиспользовать существующие API и хранилище порядка, усилив проверку границ и атомарность перед подключением управления.

### Invariants
- IV1 — Порядок эпиков меняется только внутри выбранного проекта, порядок историй — внутри одного эпика.
- IV2 — Изменение порядка не меняет родителя, задачи, спринты и релизы.
- IV3 — Некорректные или чужие UUID не приводят к частичным изменениям; сохранение атомарно.
- IV4 — После повторного чтения клиент и MCP показывают одинаковый порядок.
- IV5 — Оба уровня переставляются непосредственно на доске, без перехода в настройки или бэклог.
